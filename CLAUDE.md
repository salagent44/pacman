# pacman — project instructions

pacman is a single static Go binary that is both a token-authenticated file drop
(`pacman serve`) and the client for it (`pacman ls/put/get/install/update/rm`).
Its job is to hold the binaries we build so any machine with the token can pull
them and keep them current with `pacman update`. Read `README.md` for the API
and command reference before changing behaviour.

## Hard rules

- **No CI, ever.** Do not add `.github/workflows`, Actions, or any hosted
  pipeline. Building, testing and releasing happen on this machine with `make`
  and `gh`. If a task seems to need CI, do it locally instead.
- **One binary, stdlib only.** No third-party Go modules. Server and client stay
  in the same executable so a fresh box bootstraps with a single curl.
- **Never commit a token.** The only token that may appear in the repo is the
  literal example `devtoken`. Real tokens live in `/etc/pacman/env` on servers and
  `~/.config/pacman/config` on clients, both mode 600.
- **Names stay flat** and validated by the one regexp in `server.go`. Every route
  except `/healthz` requires the token.
- **Atomic writes everywhere.** Anything that lands on disk goes through
  `writeAtomic` (temp file beside the target, then rename).

## Build and test

```sh
make test        # go vet + go test, run before every commit
make static      # CGO_ENABLED=0, stripped, version stamped from git describe
```

Tests are hermetic: `server_test.go` and `client_test.go` spin the server up
in-process with httptest and point the client at a temp HOME. Add a test for any
new command or route.

## Shipping a binary

Two destinations, two commands:

```sh
make publish                  # build, then `pacman put` it into our drop; clients run `pacman update`
make release VERSION=v0.2.0   # build linux amd64+arm64, sha256, `gh release create` on salagent44/pacman
```

`make publish` uses the freshly built binary as the client, so it needs a
`pacman login` on this machine (see README). `make release` is how the public
bootstrap URL in the README gets a new version; tag numbers follow semver and
the release notes are generated by `gh`. Do both when a change should reach
machines that only have the release URL.

Use `gh` (as salagent44, see the global instructions) for every GitHub action:
releases, issues, PRs. Never point the user at the GitHub web UI.

## Testing on real machines

Use `virtman` (the local VM tool) rather than reasoning about deployment in the
abstract. Convention so far:

- A VM named `pacman` runs the server as a systemd service, installed with
  `sudo ./pacman serve -install`. Its token is the dev token; nothing on it matters.
- Spin up a throwaway VM (`virtman make alma10 --name X` or `ubuntu2404`) to test
  bootstrap: curl the binary, `login`, `install`, `update`, then delete the VM.
- Prove downloads from a second machine with `sha256sum` against the original.
- After changing the server, re-run `sudo ./pacman serve -install` on the VM and
  check `systemctl is-active pacman` and `journalctl -u pacman`.

## Style

- Plain `net/http` with Go 1.22 method patterns on `ServeMux`. Handlers return
  JSON errors via `writeError`.
- Keep the request log to one line per request; the token is redacted by
  `redactedPath` and must stay that way.
- Commit messages: what changed and why, wrapped at 72 columns.
